# v0.4.0 缺失语义约定（Missing Semantics Convention）

> 基线：`bac4185`（分支 `release/v0.4.0`）
> 作者：架构审查官 ｜ 关联清单：`docs/v040-失败伪装清单.json`（37 条）｜ 复核器：`scripts/check-fail-open.py`
> 状态：**待 Chief 批准**。本文不改动任何被测代码，只定义规则。

---

## 0. 为什么需要这份东西

`docs/v040-失败伪装清单.json` 里 37 条缺陷，按机制归类后有 **13 条是同一个根因的不同变体**：**"没有数据"被表达成"有数据，而且这个数据很好看"**。

它们散落在六个互不相干的层里（Rust 存储、Rust 增强、Python 聚合、Python 判定、Python 产物、React 呈现），每处的写法都不一样，但后果完全一样：

| 层 | 位置 | 缺失被表达成 | 读者会以为 |
|---|---|---|---|
| 聚合 | `evaluation/report.py:315` | `0.0` | 膨胀比是 0（等于没膨胀） |
| 聚合 | `evaluation/report.py:192` | `"complete"` | 完整交付 |
| 聚合 | `evaluation/report.py:194` | `continue` | 这条样本不存在 |
| 存储 | `src-tauri/src/storage.rs:117` | 默认 ProviderConfig | 用户就是用默认配置 |
| 后端 | `src-tauri/src/provider.rs:854` | `enhancement_level: "none"` | 模型判断不需要改 |
| 前端 | `src/lib.ts:227` | `"complete"` / `"light"` | 结果完整 |

**这就是"三次尝试改判据都失败"的机制性解释之一**：测量层没有一种统一的"这里没测到"的表达方式，于是每次改判据，改的都是某个具体位置的默认值；下次换个地方重演同一个错误，团队就以为"判据本身有问题"。**先统一缺失的语义，再谈改判据。**

---

## 1. 唯一的合法缺失表示

> **缺失 = `None`（Rust: `Option::None` / Python: `None` / TS: `null`）。**
> **没有任何其他东西可以表示"没有"。**

配套的两个必要区分：

- **观测到的 0 不等于缺失。** 0 次失败就是 `0`，它必须能和"没测到"区分开。缺失用 `None`，零用 `0`，两者不得互相顶替。
- **空集合不等于缺失。** `[]` 表示"测了，结果是空的"；缺失表示"没测"。在 Python 侧，`[]` 与 `None` 都在 JSON 里可以区分；在 Rust 侧 `Vec::new()` 与 `Option::None` 必须用不同类型区分。

---

## 2. 六种伪装（缺陷侧的六种表现）

下表是本项目里实际出现过的全部六种伪装形式，每种都给出实例位置。

### D1 零值伪装

缺失被写成 `0` / `0.0` / `false`。

```
evaluation/report.py:315   "pad_ratio": ... if cost_ratios else 0.0
evaluation/report.py:236   mean_delta = (sum(deltas.values()) / len(deltas)) if deltas else 0.0
evaluation/report.py:300   dim: round(sum(vals) / len(vals), 4) if vals else 0.0
```

**为什么最危险**：0 是一个**合法的好数字**。下游的门槛判断（`pad <= 2.0`、`worse_rate < 0.1`）拿 0 去比，天然通过。**缺失一旦变成 0，判定层就再也发现不了它。**

### D2 空串伪装

```
evaluation/export_data_pack.py:74   "...胜/平/负 = 4/3/5..."   # 整段是字面量，与数据无关
```

### D3 空容器伪装

```
evaluation/report.py:186   enhanced = sample.get("enhanced")      # 缺失时是 None
evaluation/report.py:209   deltas = judge.get("deltas", {})        # 缺失时是 {}
```

`{}` 与 `None` 在下游走同一条分支，于是"没给维度分"和"给了空维度分"无法区分。

### D4 键不存在伪装

```
evaluation/verify_enhance.py:211   q.get("question", "")   # Rust 侧字段名其实是 text（models.rs:68-72）
```

读取端用一个**猜错的键名**去取，取不到就得到空串 —— 字段不存在被伪装成"这个字段是空的"。**这一类只能用跨层等价测试发现，读代码看不出来。**

### D5 默认值伪装

缺失被补上一个"看起来正常"的默认值。危害排第二，因为它产出的是**语义错误**而不是数值错误。

```
evaluation/enhancer.py:206    out.setdefault("enhancement_level", "clarify" if ... else "light")
src/lib.ts:228                enhancement_level: result.enhancement_level ?? (... : "light")
src-tauri/src/storage.rs:126  .unwrap_or_default()          # 配置读失败 → 默认 ProviderConfig
evaluation/bench_judge.py:90  value = parsed.get("relevance")   # novelty 缺失 → 用 relevance 顶替
```

其中"指标被顶替"（relevance 顶替 novelty）最阴险：**顶替后的数值完全合法，且参与模型排名的排序键**，没有任何报错。

### D6 分母消失伪装

样本不是被写成零，而是**从分母里消失**。这是最难发现的一种，因为所有指标看起来都自洽。

```
evaluation/report.py:194   judge = result.get("judge"); if not judge: continue
evaluation/report.py:187   if isinstance(enhanced, dict) and enhanced: delivery_total += 1
evaluation/report.py:367   present_min = min((n for sc, n in scenario_ns.items() if sc in major_scenarios), default=None)
```

第三行尤其典型：只对**已经出现过的场景**取最小值。跑 20 条编程、0 条办公写作，`present_min = 20`，门槛通过 —— **缺失的场景不参与取 min，等于不存在。**

## 3. 总则

> 编号 R1–R8。清单里每一条缺陷的"验收条件"都是这 8 条之一的具体化。

| 编号 | 规则 | 反例（当前代码） |
|---|---|---|
| **R1** | 缺失只能是 `None`/`null`。禁止用 `0`、`""`、`[]`、`{}`、默认值顶替。 | `report.py:315` |
| **R2** | 观测到的 0 必须能和缺失区分。判定"这个 0 是真的 0 还是没测到"必须靠 `None` 而非数值。 | `report.py:236` |
| **R3** | **判定层 fail-closed**：判定层拿到 `None` 必须判 **FAIL**（或显式判"不可判定"并把该门槛标为不可用），绝不允许沿用上次的值、默认值或直接跳过。 | `release_gate.py` 原来只判 `None` 是对的，但上游给它的是 `0.0` ⇒ fail-closed 被下移了一层 |
| **R4** | **分母显式化**：每个比率指标必须携带 `n`；被排除的样本必须单独计数（`excluded`）并记录原因，且这个计数与 `n` 一起落进产物。 | `report.py:194` |
| **R5** | **缺失向上传播**：聚合时若任一组成项缺失，聚合结果缺失（`None`），不是 `0`。 | `bench_report.py:68` `float(value or 0)` |
| **R6** | **呈现层必须显示"不可判定"**：缺失的指标在报告与 UI 里必须显示为不可判定，禁止渲染成 `0.00×`、`0.0%`、`—`（看起来像 0）。 | `report.py:584` |
| **R7** | **跨层一致**：同一个字段在 Rust struct / zod / TS / Python 四处的缺失表示必须一致，且由测试读取对方源码做断言（不许断言自己这一侧的硬编码期望值）。 | `enhancer.py:1-5` 声称 5 项等价，实际只有 2 项被钉住 |
| **R8** | **身份可追**：缓存键、resume、产物文件名、meta 四者必须编码自身身份（模型 / 温度 / 提示词版本 / 样本集版本 / run id），否则产物不可证伪。 | `run_eval.py:904` 缓存键不含这些 |

## 4. 分层落地规则

### 4.1 采集层（`src-tauri/src/provider.rs`、`evaluation/run_eval.py`）

| 允许 | 禁止 |
|---|---|
| 失败原因以**独立字段**表达（`error_code`、`notices`、`delivery_status`） | 把失败编码成业务正常值（`enhancement_level: "none"`） |
| 每个样本无论成败都进入统计分母 | `continue` 跳过失败样本 |
| 记录 `status`（success / error / partial） | 把 error 记成 success，或用 0 代替成本 |

> `provider.rs:854/872` 的 fallback 结果必须携带独立的失败原因字段，`enhancement_level` 只允许来自模型判断。

### 4.2 存储层（`src-tauri/src/storage.rs`）

| 允许 | 禁止 |
|---|---|
| 读失败返回 `Err` | `.ok()` + `.unwrap_or_default()` 静默回落默认配置 |
| 写凭据与写配置分两条路径 | 一个函数同时能被"设置页"和"导入包"调用 |
| URL 校验下沉到存储层 | 校验只在命令层（导入路径绕过） |
| 返回结构化报告（`imported` / `skipped`） | 静默 `take(N)` 截断 |

### 4.3 聚合层（`report.py`、`bench_report.py`、`judge.py`、`bench_judge.py`）

| 允许 | 禁止 |
|---|---|
| 指标缺失 → `None` | `else 0.0` |
| 指标缺失 → 从排序键里退出（该模型标为不可评） | 用别的指标顶替（relevance → novelty） |
| 每个维度各自计算相关性 | 一个 rho 复制成 5 份 |
| 未知状态归入 `unknown` 桶 | 未知状态归 `complete` |

### 4.4 判定层（`release_gate.py`、`gate_check.py`）

| 允许 | 禁止 |
|---|---|
| 缺失 → FAIL | 缺失 → PASS |
| 门槛不可判定时显式报"不可判定"并禁止发布 | 门槛不可判定时静默跳过 |
| 阈值引用噪声地板时写明"低于地板不可解读" | 阈值取自"同配置多跑里较好的一次" |

### 4.5 呈现层（`report.py` 的 Markdown、`src/views/*.tsx`）

| 允许 | 禁止 |
|---|---|
| 缺失 → "不可判定" / "未测量" | 缺失 → `0.00×` / `0.0%` |
| 失败 → 显示失败原因 | 失败 → 显示"无需修改"这类**判断性**文案 |
| 分母与被排除数一起显示 | 只显示比率 |

### 4.6 前端契约层（`src/types.ts`、`src/lib.ts`）

| 允许 | 禁止 |
|---|---|
| 可选字段用 `?` / `null` 显式声明 | 声明了却让后端永远不会发的事件分支留着 |
| 缺失时显示"结果不完整" | `?? "complete"` / `?? "light"` |

## 5. 可执行检查

### 5.1 禁用模式扫描（建议进 CI）

```powershell
# 聚合层：缺失被写成 0
Select-String -Path evaluation\*.py -Pattern 'else 0\.0' -Encoding UTF8
# 聚合层：指标被顶替
Select-String -Path evaluation\*.py -Pattern 'scores\.get\("relevance"\)' -Encoding UTF8
# 存储层：读取失败静默回落
Select-String -Path src-tauri\src\*.rs -Pattern 'unwrap_or_default\(\)' -Encoding UTF8
```

扫描结果必须**逐条在清单里有对应条目**，否则算新增缺陷。

### 5.2 清单复核器

```powershell
python scripts\check-fail-open.py          # 逐条复核，退出码非 0 表示还有 P0 未闭环
python scripts\check-fail-open.py --json   # 机器可读输出
python scripts\check-fail-open.py --only A,C
```

复核器的两条纪律（与本约定同源）：

- **探测不到 ≠ 通过。** 找不到目标代码块时报 `UNVERIFIED`，不报 `FIXED`。
- **人工项不自动通过。** `kind=manual` 的条目只报 `UNVERIFIED`，必须由人给出结论。

### 5.3 建议的门禁接线

```
release_gate.py  ──读取──▶ docs/v040-失败伪装清单.json
                            │
                            └──scripts/check-fail-open.py ──▶ 存在未闭环 P0 ⇒ 退出码 1 ⇒ 门禁 FAIL
```

**门禁的判据里必须包含"测量层自身可信"这一条**。判据不可信时，测出来的任何数字都不能进发布决策。

## 6. 例外与豁免

1. **真实 0**：0 次失败、0 个候选、0 成本是合法观测值，用 `0` 表示，不得改成 `None`。判断标准是"我们测过了"。
2. **错误码与提示**：属于"已知的失败"，用独立的 `error_code` / `notices` 字段表达，不占用数值字段。
3. **UI 的"未配置"**：前端未配置状态不属于测量缺失，可用 UI 专有的 `null` + 空态渲染，但**不得复用业务字段**。
4. **历史遗留产物**：v0.3.2 及以前已产出的 JSON 不回改；它们只能标注为"历史产物，口径见 v040-效果测量方案.md"，不得与 v0.4.0 产物混算。

## 7. 与验收的对应关系

本文的 R1–R8 与 `docs/v040-失败伪装清单.json` 的 `acceptance` 字段一一对应：清单每一条的验收条件，都是某条规则在该位置的具体化。**清单是规则的实例，本文是规则本身** —— 修清单里的条目时如果发现规则本身有漏洞，改本文，不要在条目上打补丁。
