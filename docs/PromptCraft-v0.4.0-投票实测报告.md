# PromptCraft v0.4.0 实测报告：档位投票是否有用

> 执行日期：2026-10-04
> 脚本：`evaluation/verify_vote_stability.py`
> 数据：`evaluation/results/v040_vote_raw_clear_medium_k3.json`
> 成本：240 次 API 调用
> 底模 `deepseek-flash`，temperature 0.1（与产品 `provider.rs` 一致），提示词 `promptcraft-v2.2.0`

---

## 一、结论

**否。「2 次并行采样 + 多数决定」在数学上不可能生效，实测也完全没有生效。**

| 指标 | clear | medium |
|---|---|---|
| 单次调用翻转样本 | 9/20 = 45% | 3/19 = 16% |
| **投票后翻转样本** | **9/20 = 45%** | **3/19 = 16%** |
| 逐次调用分歧率（A≠B） | 18/60 = **30%** | 8/57 = **14%** |
| **投票改过结果的次数** | **0/60** | **0/57** |

翻转样本集合完全相同（clear 9/9、medium 3/3，「仅投票后翻转」= 0）。
全量 **117/117 次**点击中，`vote` 恒等于第一次采样的档位。

---

## 二、为什么必然如此

多数投票的定义要求 n ≥ 3。n = 2 时：

- 两次相同 → 一致，`is_uncertain = false`
- 两次不同 → **1:1 平局**，按首次出现破平局 → 必然取 A

所以 `majority_vote([A, B]) ≡ A`，**恒等式，与模型无关**。

这个错误来自实现：self-consistency 的原始实现是 n = 5（`paths: int = 5`），
照搬了它的**结构**却把 n 缩到 2，把「多数」退化成了「第一个」。

> 修正：`provider.rs` 与 `models.rs` 的注释已改写为「它不改变任何决策」，
> 并写明实测数字。用户可见的提示文案本来就是正确的
> （n=2 时 `is_uncertain` 蕴含 `is_tie`，实际只会弹「已按首次结果呈现」那句），
> 带「已按多数决定」的分支在 n=2 下不可达，是为将来 n=3 预留的。

---

## 三、更重要的发现：跨点击漂移不在「单次调用内部」

12 个翻转样本里有 **2 个**（`translate_product_manual`、`creative_story_opening`）
**每一次点击内部两次采样都完全一致，三次点击之间却跳了**：

```
translate_product_manual  三次点击档位 = ['light', 'none', 'light']   每次内部 light/light、none/none、light/light
creative_story_opening   三次点击档位 = ['none', 'none', 'light']    每次内部两次均一致
```

**这说明模型对这两条提示词的档位判断是双峰的**：单次调用内部它很确定
（两次采样必然落在同一个峰），但不同点击会落在不同的峰。

**推论：任何「点击内投票」都治不了这个。** n = 3 也一样 ——
如果双峰足够尖锐，3 次采样也会全部落在同一个峰上（正如这 2 个样本 n=2 时 0 分歧）。

这与「温度降到采样噪声的极限（0）后仍有 26–40% 翻转」的实验完全一致：
**漂移来自采样的独立性，不是采样的随机性。**

> 换句话说：一直在调的是「单次调用有多随机」，但真正的问题是
> **「这个分布在双峰之间」**。降温度只能压前者。

## 四、副产品：一个统计功效更好的指标

逐次调用分歧率（单次点击内两次独立采样的不一致比例）：

| | clear | medium |
|---|---|---|
| 分歧率 | **30%** | **14%** |

它比「翻转率」好用，理由有三：

1. **样本量是 60 / 57 个点击**，而翻转率只基于 20 / 19 个样本；
2. **不受跨运行噪声影响** —— 之前两次相同配置的 clear 实验给出 30% 与 71%，
   噪声地板高达 41 个百分点；本指标在单次点击内测量，绕开了这个问题；
3. **直接可解释**：30% 就是「用户点一次增强，模型有 30% 的概率自己前后不一」。

分歧最集中的样本：`meeting_minutes`（clear，办公写作）**3/3 次点击都分歧**，
但 A 侧稳定 light —— 分歧全在 B 侧。

---

## 五、建议

### 5.1 投票功能：改为纯检测，不做决策

保留 `is_uncertain` 信号的产出（结果区提示「2 次采样出现平局，建议重新生成」），
去掉「多数决定」的措辞。理由：

- 它换不到更稳定的档位（实测 0/117）；
- 但 30% / 14% 的自相矛盾率是**真实且此前不可见的产品信息** ——
  用户据此知道该重试还是该接受；
- 代价是 2 倍 token。

### 5.2 要真正解决漂移，只有三条路

| 方案 | 可行性 |
|---|---|
| 降温度到 0 | ❌ 已实测，仍有 26–40% 翻转 |
| 加大 n（3/5/…） | ❌ 理论上降低单次方差，但 §三 证明本问题在跨调用而非调用内 |
| **把档位决策从 LLM 手里拿走**（规则化 / 前置分类器 / 让用户在两个结果里选） | ✅ 目前唯一未被否定的方向 |

---

## 六、诚实边界

1. 本轮只测了 clear + medium 两档 39 条样本、每条 3 次点击。
   severe 档未测（其 baseline 翻转率仅 10%，空间小）。
2. `vote == A` 命中 100% 是**结构性必然**，不是实验观察 ——
   实验只是确认了实现与推导一致。
3. 温度固定在 0.1，**没有测 n=3**。§三 的推论基于「双峰足够尖锐」这个观察，
   而这个观察只有 2 个样本支撑，**不是普适结论**。
4. 「跨点击漂移来自采样独立性」这一判断，与温度降到 0 的实验结论方向一致，
   但两者都只覆盖 20 条样本 × 3 次，统计功效有限。
