## B. 状态可见性

### B-1. 「配置已保存」这类结论性文案的正确形式

**结论：一个合格的状态文案必须回答三个问题——「做了什么」「凭什么是真的」「还剩什么没做」。**

「已保存」只回答了第一个，而且回答的是**动作**不是**状态**。用户真正关心的是"我现在能不能用"。

| 形式 | 文案 | 评价 |
|---|---|---|

落点：`src/App.tsx:293` `setProviderMessage("")` 改为结构化对象（`{ verified, written, pending, detail }`），`src/views/SettingsView.tsx:18` 按三段渲染。

### B-2. 保存凭据 vs 导入配置，UI 上怎么区分

**后端已经分开了，UI 没有。**

- 后端：`src-tauri/src/lib.rs:52-70` 保存命令的凭据是**独立参数** `api_key`；`src-tauri/src/storage.rs:186-192` `save_provider_config` 注释写明「配置保存路径不得有写凭据的能力」；`storage.rs:475` 导入路径再显式 `provider.api_key = None`。
- UI：`src/views/SettingsView.tsx:18` 有一个「验证并保存」按钮（写凭据 + 写配置）；`src/views/SettingsView.tsx:21` 在**「剪贴板与隐私」**区块的**「历史保留 90 天」**那一行里放了「导出数据 / 导入数据 / 清空全部本地数据」三个按钮。

**问题**：一次导入会改写**四类东西**（历史记录 / 本机设置 / 供应商配置 / 容量上限），却和「清空全部本地数据」并排放在一个讲保留策略的区块里，共享同一个 `dataMessage` 字符串。

**建议的三点区分：**

1. **导入/导出独立成块**，标题「本地数据导入 / 导出」，并在按钮上方写清「导入会覆盖：本机历史记录、设置、供应商配置（含价格）」——**覆盖前先说会覆盖什么**。
2. **导入前给预览**：后端返回结构化 diff（哪些字段会变、哪些被忽略），前端渲染成清单（见 A-3.2 文案）。当前 `src-tauri/src/models.rs:150-162` 的 `ImportReport` 只有 `imported / skipped / base_url_kept` 三个字段，**不足以描述"配置被改了"**，需要扩展。
3. **保留凭据路径的不可见性，并在导入结果里重申**：「导入包不含也不接受 API Key；本机 Key 保持不变。」——`src/views/SettingsView.tsx:21` 已有「导出包不包含 API Key」的说法，导入侧应补对称的一句。

**关于"共用一个 DTO"**：后端已把**凭据**从 `ProviderConfig` 里摘出去（`src-tauri/src/models.rs:143-144` 的 `skip_serializing, skip_deserializing`），这一层是干净的。真正还共用 DTO 的是**导入包与设置页**——两边都用 `ProviderConfig`（`provider.json`），所以导入能改价格与默认模型（见 A-3.2）。建议引入一个**导入专用的收窄 DTO**（只允许 `models` / `default_model` / `v4_flash_model_id`，**不含** `input_price` / `output_price` / `base_url`），或在 `storage.rs:501` 之前显式保留本机价格与端点。

### B-4. 错误提示应该给到什么粒度

**结论：默认给「结论 + 下一步」，原始报错折叠在后面，不主动占据视觉重心。**

理由：纯结论会让用户无法自助（分不清是代理、Key 还是服务端）；纯原文会让用户读不懂（`src-tauri/src/provider.rs:126` 后面跟的是 reqwest 的原始错误，含完整 URL）。分层两者都不牺牲。

**而且这条几乎是零成本的**——错误码已经在管道里了，只是被丢掉了：

- `src/types.ts:129-135` `BackendEvent` **已经定义了** `code?: string` 和 `message?: string`。
- `src/lib.ts:79` `if (event.type === "error") { reject(new Error(event.message ?? "增强失败")); return; }` —— **`event.code` 在这里被丢弃**。
- 后端 `src-tauri/src/provider.rs:808-831` 已经产出了完整错误码：`AUTH_FAILED` / `BALANCE_INSUFFICIENT` / `MODEL_NOT_FOUND` / `RATE_LIMITED` / `NETWORK_FAILED` / `TIMEOUT` / `NETWORK_UNREACHABLE` / `STREAM_INTERRUPTED`。
- 但 Rust 侧 `src-tauri/src/models.rs:175-182` 的 `BackendEvent` 枚举**没有 Error 变体**（只有 Delta/Status/Result/Usage），错误是走命令的 `Err(String)` 回来的，所以 `code` 根本到不了前端。

**建议的三级错误对象**（`src/types.ts` 加一个 `EnhanceFailure`）：

```ts
{ code: string;          // AUTH_FAILED / TIMEOUT / ...
  summary: string;       // 一句话结论
  nextStep: string;      // 用户下一步做什么
  detail?: string;       // 原始报错，默认折叠
}
```

落点：`src-tauri/src/models.rs:175-182` 补 `Error` 变体或让命令返回结构化错误 → `src/lib.ts:79` 保留 `event.code` → `src/views/EnhanceView.tsx:173` 错误横幅改成三段式 + 可展开。

> 注：清单 B5（`src-tauri/src/models.rs:177`，P1，OPEN）已经指出了 Rust `BackendEvent` 与 TS `BackendEvent` 的契约不一致。**我的建议是选 B5 的第一条路（Rust 补 Error 变体并真的发出来）**，因为错误码已经在 `provider.rs:808-831` 产出，只差最后一段管道。

## C. 关键决策点

### C-1. 三个会引导用户做出错误决定的地方

**决策点 1：设置页的「验证并保存」——用户以为"保存"包含了"验证"**

- 位置：`src/views/SettingsView.tsx:18`（按钮）→ `src/App.tsx:292-303`
- 当前行为：一次点击同时做三件事——联网验证 Key（**仅当 Key 输入框非空**，`src/App.tsx:295`）、写凭据、写配置，然后显示一句话「连接验证成功，配置已保存」。
- **会引导的错误决定**：用户只改了模型列表、Key 留空（因为上次已经配过了），看到「连接验证成功」就认为**地址、Key、模型三者都验证过了**。实际上这次**一次网络请求都没发**。更糟的情况是：用户改了 base_url 到新的中转地址，Key 留空 → 完全没有验证 → 保存成功 → 下次增强才第一次真正用新地址发请求，失败时的报错与"刚验证过"的心理预期直接矛盾。
- **修正方向**：把「连接验证」从「保存」里拆出来，做成一个**独立的、可选的按钮**（"测试连接"），保存只负责写入；两者结果分开陈述。

**决策点 2：失败之后点「重新生成」——用户以为"重新生成"能修好**

- 位置：`src/views/EnhanceView.tsx:204`（按钮）→ `src/App.tsx:283` `regenerate` → `src/App.tsx:158`
- 当前行为：失败后 `src/App.tsx:158` 已经把上一版结果清空（`setResult(null); setOutput("")`），结果区是空的，只有一条错误横幅。点「重新生成」= 原样再发一次。
- **会引导的错误决定**：错误是"Key 没存进去"（不可重试）、"余额不足"（不可重试）、"网络不通"（可重试）三类，用户分不清。界面给的唯一出口是「重新生成」，等于暗示"再试一次就好"。用户会反复点 5 次，**每次都产生一次真实的 API 失败记录**（`storage.rs:509-533` 有记账），而错误文案每次一模一样。
- **修正方向**：按错误码给出**不同的出口**——可重试的（TIMEOUT / NETWORK_UNREACHABLE / RATE_LIMITED）给「重试」；不可重试的（AUTH_FAILED / BALANCE_INSUFFICIENT）给「去设置页检查 Key」/「去供应商充值」这类**指向性**按钮。错误码已在 `provider.rs:808-831`，只是没传到 UI（见 B-4）。

**决策点 3：「导入数据」——用户以为"导入"= 恢复历史备份**

- 位置：`src/views/SettingsView.tsx:21`
- 当前行为：一次导入改写历史记录、本机设置、**供应商配置（含价格）**、容量上限；提示只有一句话。
- **会引导的错误决定**：用户从同事那拿到一个"备份包"导入，**价格表被改成了对方的**（见 A-3.2）。此后 `src/App.tsx:153-155` 的月度强制额度按新价格计算——额度可能提前触发，也可能因为价格被调低而**超额消耗**。用户从头到尾不知道自己的计费口径变了。
- **修正方向**：导入前给变更预览，导入后逐项列出「已导入 / 未导入 / 被忽略 / 被改写」四类结果。

**（附）决策点 4：结果区的「增强等级」徽标——用户以为那是模型的判断结论**

- 位置：`src/views/EnhanceView.tsx:192`（徽标）、`:212`（摘要行）
- 当前行为：显示「无需明显修改」/「轻度增强」/「需要澄清」。
- **会引导的错误决定**：看到「轻度增强」就认为"这版一定比我的原文好"；看到「无需明显修改」就认为"我的提示词写得没问题"。但 none/light 的边界**客观不可判**（效果验证官 `docs/v040-效果测量方案.md` §1.3：「改判据之所以两次都失败，是因为它试图把一个连续量变成离散判定，而这个连续量的可判边界不存在客观标准」），且实测同一句清晰提示词重复调用有相当比例会给出不同档位（投票实测报告 §一）。**用"模型判断"这种措辞包装一个不可判的量，是把产品的判断力借给了一个摇骰子。**
- **修正方向**：徽标改说**这一版的形态**（"未改动原文" / "局部改写" / "先给了临时版本 + N 个问题"），不断言"模型判断了什么"。这与效果验证官 §2.4 的建议（把 `enhancement_level` 从产品承诺降级为内部实现细节）方向一致。

### C-2. 两处「诚实」与「顺滑」的取舍

**取舍 1：请求失败时，上一版好结果要不要保住？**

| 方案 | 做法 | 代价 |
|---|---|---|
| 顺滑 | 保留上一版结果 | 若不标注，用户会以为这就是本次的结果 ⇒ **不诚实** |
| 诚实（激进） | 清空，结果区显示"本次没有结果" | 用户为一次网络抖动**丢掉已经付过费的好结果**，且要重新请求（再花钱） |
| **诚实 + 顺滑（我选）** | **保留上一版结果，并明确标注它是哪一次** | 需要一个"陈旧结果"状态，界面多一个标记 |

- **我选第三种。** 理由：诚实的定义是"用户知道自己在看什么"，不是"把东西藏起来"。标注"这是上一次的结果（17:32）"已经足够诚实；而清空会让一次 30 秒的网络抖动变成真实的金钱损失。这是本项目**唯一**一处我认为"清空"是过度惩罚的地方。
- 落点：`src/App.tsx:158` 不在**失败路径**上丢弃旧结果（流式期间清空显示区可以接受，失败后要取回）；`src/views/EnhanceView.tsx:192` 的面板标题旁加「上一次结果」标记。
- **这与 A-4.1 的文案是同一件事的两面**：错误横幅说清"本次没成功"，结果区说清"下面是哪一次的结果"。

**取舍 2：原始报错要不要给用户看？**

| 方案 | 做法 | 代价 |
|---|---|---|
| 顺滑 | 只给"网络连接失败，请检查网络后重试" | 用户无法自助；代理、Key、余额不足三类问题长得一样，**用户只能来问** |
| 诚实（激进） | 原样把 reqwest 错误糊在横幅上 | 含完整 URL 的噪音串，**用户读不懂等于没给**；还可能让用户误以为是自己输入的问题 |
| **分层（我选）** | **默认只给「结论 + 下一步」，原始报错收在「技术细节」里，需要时一键展开** | 多一个折叠交互；但两种诉求都满足 |

- **我选分层。** 理由：分层不等于隐藏——信息还在，只是不默认占屏。而且这条几乎零成本：错误码已经产出（`provider.rs:808-831`），只差 `src/lib.ts:79` 一行不把它丢掉。
- 落点：`src/lib.ts:79` 保留 `event.code`；`src/views/EnhanceView.tsx:173` 的错误横幅改为三段式 + 可展开。

**（附）取舍 3：fallback 时要不要保留「增强器判断无需修改」这句？——删掉。**

- 备选是"保留但加限定词"（"增强器判断无需修改（本次未成功获取判断）"）。
- **我选直接删。** 理由：这句话在 fallback 路径下**描述的事件没有发生过**（清单 E1 / E2）。加限定词等于让用户自己去解析一句反事实的话，比不说更糟。改为事实陈述"本次没有增强，已保留原文"即可——**失败时不需要判断性文案**。
