# PromptCraft v0.2.2 → v0.3.0 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development 或 executing-plans 逐任务执行。
> 依据:docs/PromptCraft-v0.2.1-v0.3.0-iteration-spec.md §5(v0.2.2)、§6(v0.3.0)、§7、§10。v0.2.1 已完成(main)。

**Goal:** v0.2.2 实现增强必要性判断(none/light/clarify)与最小干预、任务感知预检、结果解释;v0.3.0 建立可信效果评测(60 样本三档模糊、A/B/C 三组对照、3 次重复、双裁判+人工校准、发布门槛)并产出"正式版"。

## Phase 1: v0.2.2 后端 — 提示词 v2.1.0 与必要性判定

### Task 1.1 SYSTEM_PROMPT v2.1.0(prompts.rs + enhancer.py 字节同步)
- 版本 `promptcraft-v2.0.0` → `promptcraft-v2.1.0`(prompts.rs:4 / enhancer.py:18)。
- 在 prompts.rs SYSTEM_PROMPT 增加(保留 v2 全部内容,新增段):"工作方式"加一步"先判断增强等级 enhancement_level"。
- 增加 `enhancement_level` 三段定义(规格 §5.2 原文):`none`(目标/关键输入/交付物明确→primary 基本保留原文,changes 可为空,0-5 条可选建议)、`light`(缺 1-3 个要素→只补必要内容,优先局部改写,不重复已有约束)、`clarify`(缺关键信息→最多 3 问+假设临时版)。
- JSON 契约加入 `"enhancement_level":"none|light|clarify"`;"suggestions 必须恰好 5 条"改为 **"可以给 0-5 条可选建议,不再要求恰好 5 条"**。
- 同步 enhancer.py(字节一致),更新 test_enhancer.py 相关期望(版本、模板前缀不变,系统提示词内容变了字节一致测试自动覆盖)。

### Task 1.2 Rust 校验放宽(provider.rs)
- `validate_complete_result`(provider.rs:591):`suggestions.len() == 5` → `<= 5`;保留 kind/operation/id 校验。
- 确认 enhancement_level 通过模型 JSON 透传(已有 serde);none 时 changes 可空(已有 empty-before 规则,无需改)。
- 提示词级版本入库:App.tsx:190 的 persistHistory 补传 `promptVersion: "promptcraft-v2.1.0"`(前端常量,来自后端结果或模块常量)。

### Task 1.3 验证
- `cargo test`(20)+ pytest(test_enhancer.py 字节一致 15 项)+ 前端 `npm test`。
- 提交:`feat(prompt): v2.1.0 enhancement-level judgment and 0-5 suggestions`(prompts.rs/provider.rs/enhancer.py/test_enhancer.py/App.tsx 一起或拆 2 提交)。

## Phase 2: v0.2.2 前端 — 任务感知预检与结果解释

### Task 2.1 任务感知预检(preflight.ts 重构)
- 新增 `export type PreflightTask = "code"|"creative"|"writing"|"qa"|"data"|"translation"|"other"` 与 `classifyTask(text): PreflightTask`(轻量启发式,关键字+结构判断,规则见规格 §5.3 最低分类集合)。
- 重构 `preflight(text, hasContext, taskType): PreflightFinding[]`:按任务类型检查(代码→代码/错误/运行环境/预期行为;翻译→原文/目标语言/格式;创意→用途/受众/风格边界;写作→读者/用途/语气/篇幅;qa→对象/事实边界;data→字段/口径/时间范围/指标;other→目标/上下文/交付物)。**每次最多 3 条,按影响排序**,仍只提示不拦截。
- EnhanceView.tsx:调用点(L80)改为 `preflight(original, context.length>0, classifyTask(original))`;deps 增加;卡片仍非阻塞。
- preflight.test.ts:新增任务分类与按类型检查用例(覆盖规格 §5.3 各类型)。

### Task 2.2 结果解释摘要(规格 §5.4)
- 结果区新增只读摘要卡(EnhanceView,基于 result + original,零额外调用):
  - 增强等级(enhancement_level → 无需明显修改/轻度增强/需要澄清)
  - 长度变化:`原文 N 字 -> 结果 M 字(x.xx 倍)`
  - 修改摘要:由 changes 类型推导(规格 §5.4 六类映射),无 changes 显示"无实质修改"
  - 事实来源:assumptions 非空 → "包含明确假设";否则"仅使用用户提供内容"
- 样式:`.result-summary` 卡片,只读。

### Task 2.3 变更接受/拒绝重建规则(规格 §5.5)
- `applyChangeDecision`(lib.ts)改为只替换**第一个完全匹配**片段(现有 replace 已近似,补"未命中 anchor/before 时不静默改其他位置,返回错误标记")。
- insert 建议只追加到段落末尾或明确 anchor 后(调整 applySuggestionToText:无 anchor 时仅追加到末尾,不随机插入)。
- 接受/拒绝/恢复原文/手动编辑统一进撤销栈(现有 commitOutput 已覆盖,补 keepEssentialEdits 与 restoreOriginal 已进栈——v0.2.1 已完成,仅核对)。
- 切换候选/重新生成时保留上一版为历史版本:新增 `sessionVersions: string[]`,每次 result/手动编辑前 push 当前 output;UI 提供版本回退(轻量:仅保留最近 5 版)。

### Task 2.4 提交与验证
- 提交:`refactor: make preflight checks task aware`、`feat(ui): enhancement result explanation summary`、`fix(ui): change/suggestion rebuild rules and version history`。
- 每提交 `npm test && npm run build`;前端测试新增:任务分类、按类型预检、结果摘要文案、change 未命中提示。

## Phase 3: v0.2.2 验证门槛(规格 §5.1/§5.6)

- 表驱动测试:以规格 §5.6 的 8 条典型请求(中暑症状/这是什么意思/学生码农办公/扫描 skill/只保留 brainstorming/opencode 右侧窗口/真实爱情帖子/河北科技学院大三课程)为输入,断言:任务类型识别、风险识别、是否编造、该澄清时给问题、保留意图、避免无意义扩写。放 `evaluation/` 或前端测试(纯函数驱动,不依赖唯一文案)。

- 提交:`test: cover task classification and minimal-intervention gates`。
- 门槛不达标时回到 Phase 1 微调提示词(最多 2 轮)。

## Phase 5: v0.3.0 评测管线(规格 §6.3/§6.4/§6.5)

### Task 5.1 三组对照强制化(A 原始 / B 填充 / C 增强)
- `--control-group` 升级为默认核心模式:每个样本恒生成 A/B/C 三变体;`pad_to_length` 保证 B 与 C 字符数差 ≤5%(现有函数已近似,补目标长度精确化);报告主比较 C-B,A-B 辅助。保留 `--no-control-group` 逃生开关。

### Task 5.2 重复实验 `--repeats N`(默认 1;正式运行用 3)
- run_eval:infer+judge 按 repeats 循环(缓存键加 `_rep<i>`;`--skip-infer/--skip-judge` 复用);聚合按 repeats 取均分/多数胜。
- model_benchmark:同机制。
- 配置:`config.yaml run.repeats` 与 `benchmark_config params.repeats`。

### Task 5.3 每次对比元数据(规格 §6.4)
- run_eval infer 循环记录 wall-clock `latency_s`(timing 包住 adapter.infer);输出 token 估算 `chars/1.8`;错误码字符串已存;model id=target。写入 detail/raw。
- model_benchmark 已有 latency/usage;补 error 码字符串规范化。

### Task 5.4 裁判盲化 + 目标模型与增强器/裁判解耦(规格 §6.5)
- **主裁判保持 deepseek-v4-flash(plan);增强器保持 deepseek-v4-flash(DeepSeek API)。**(用户决策:不更换裁判。)
- **目标模型改为当前火山 plan 端点可用且 ≠ deepseek-v4-flash 的模型**:先运行探测脚本(plan 端点 `/v1/messages` 逐个探测候选模型,如 doubao-seed-2.0-mini / glm-5.2 / doubao-seed-1-6 系列 / qwen 系列 / kimi 系列),取可用集合剔除 deepseek-v4-flash 作为正式目标列表(期望 doubao-seed-2.0-mini + glm-5.2 + 至少 1 个额外可用模型;若只有 2 个则接受)。
- cross_check 保持 false(单裁判 deepseek-v4-flash 即满足"主裁判≠目标模型部署");若需第二裁判再启用。
- A/B/C 标签随机化、盲评:judge_pair 已随机 A/B;三组对照采用 C-B 与 A-B 两两,提示词标签中立化(不含"原始/增强"字样)。
- 人工校准:`review_export.py` 导出 ≥20% 有效比较(任务+三提示词+三回答,无内部标签)。

### Task 5.5 提交与验证
- 提交:`feat(eval): mandatory ABC control group and repeats`、`feat(eval): blind judging with primary judge decoupled from enhancer`、`feat(eval): per-comparison metadata capture`、`feat(eval): human calibration workflow`。
- 单测:repeats 缓存键、ABC 长度差≤5%、blind 标签中性断言、元数据字段存在。

## 反模式守卫
- 不把"恰好 5 条建议"作为核心成功条件;不本地编造建议/假设。
- 不引入不存在的 API(`--repeats`/门槛逻辑从零实现并单测)。
- 主裁判与增强器不得同模型部署;裁判提示词不得含"原始/增强"标签。
- 报告门槛必须显式渲染,不得静默跳过。
- 每阶段独立提交 + 对应子系统测试;阶段结束跑 `build-check.cmd test`。

- v0.2.2:§5.1 五条 + 表驱动测试通过 + 回归集门槛达标。
