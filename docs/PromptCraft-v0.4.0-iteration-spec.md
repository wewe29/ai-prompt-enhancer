# PromptCraft v0.4.0 迭代实施规格：降温度与澄清质量

> 文档状态：基线规格（可实施；后续可能被团队方案修订）
> 基于版本：PromptCraft 0.3.5
> 适用项目：`F:\ai-prompt-enhancer`
> 编写日期：2026-10-01
> 上游依据：`docs/PromptCraft-v0.3.1-v0.5.0-iteration-spec.md`（原 v0.4.0 = 本地个性化画像，**本轮推迟**）
> 本轮依据：`docs/PromptCraft-v0.4.0-效果验证报告.md`、`docs/PromptCraft-v0.4.0-投票实测报告.md`

## 1. 文档目的

v0.4.0 的范围：

1. **把采样温度从 0.35 降到 0.1**（`src-tauri/src/provider.rs`）—— 唯一被数据证明有效的改动
2. **禁止提问用户已经说过的信息**（系统提示词 v2.2.0 → v2.5.0）—— 人工盲评实测 11% 命中率的纯逻辑缺陷
3. **给样本集补「澄清质量」标注字段** —— 让该缺陷可被机械门禁拦住

**明确不再做的：收紧 none/light 判据。** 两次尝试（none 判定清单 v2.3.0、light 正向条件 v2.4.0）均以 light 被大面积压制、稳定性不升反降告终。详见《v0.4.0 判据实验记录》。

**为什么必须先降温再看别的**：clear 档 0.35 → 0.1 的翻转率从 55% 降到 30%（约 2.5 个标准误），并顺带消除了 clear 档 2 次「本该克制却转 clarify」的过度补全。

## 2. 当前基线

### 2.1 测量条件与线上一致

| 位置 | 值 |
|---|---|
| `src-tauri/src/provider.rs` | `"temperature": 0.35` ← **产品实际值，本轮要改的就是它** |
| `evaluation/verify_stability.py` | `TEMPERATURE = 0.35` |

除温度实验外，其余实验数据均在此条件下取得，**可直接外推到线上行为**。

### 2.2 已实现（本轮不重做，不得回退）

- 系统提示词 `promptcraft-v2.2.0` 的全部结构。
- **`clarify` 判据一字不改** —— 它的定义带具体反例（「这是什么意思」但没有对象），20/20 三次全稳，是本项目唯一被验证有效的判据写法。
- 交付状态 complete/partial/fallback 全链路 —— 360 次运行零漂移。
- `none` 等级的「建议直接使用原文」非阻塞引导、结果过长时的「可精简」提示。

### 2.3 真实差距（本轮要做的 3 项）

| # | 差距 | 现状证据 |
|---|---|---|
| 1 | **档位判断不稳定**：clear 档 20 条 × 3 次，11 条在 `none`/`light` 间翻转（55%） | 效果验证报告 §三 |
| 2 | **会问用户已经说过的信息**：翻译场景 20 条盲评命中率 11%（办公写作 100%） | 效果验证报告 §四 |
| 3 | **样本集无法标定澄清质量**：`expected_behavior` 只能标定「该不该澄清」，翻译类 20/20 档位恰当却仍 11% 命中 | 效果验证报告 §四.5 |

## 3. 总体实施原则

- **本轮是配置与提示词修正，不是架构改动。** 改动面：`provider.rs` 一个数值 + `prompts.rs` 一段追加 + 样本集一个字段 + 评测脚本一个函数。
- **`clarify` 判据是资产，不得改写。**
- **验收指标必须同时看「稳不稳」和「还有没有在干活」。** 翻转率 0% 既可能是判得准，也可能是 light 全判没了；恰当率在「判 none」方向上虚高，因为 `expected=light` 时判 `none` 也算恰当。**任何只报单一指标的验收都是无效的。**
- 系统提示词变更必须同步 `evaluation/enhancer.py` —— `evaluation/test_enhancer.py` 逐字对照 Rust 源码断言一致。

## 4. v0.4.0 详细需求

### 4.1 温度 0.35 → 0.1

**修改**：`src-tauri/src/provider.rs` 的 `"temperature": 0.35` → `0.1`。

**不做的事**：不降到 0。temp 0.1 → 0 无进一步改善（30% vs 40% 在噪声内），且降到 0 会牺牲候选多样性而无实测收益。

**同步**：`evaluation/config.py`、`evaluation/config.yaml`、`evaluation/enhancer.py` 的默认值一并改为 0.1。
> v0.4.0 代码审查 H5 发现：这三处长期是 0.35，而 `config.yaml` 的注释却写着「与 PromptCraft 后端一致」——**注释声称一致却长期不一致，比没有注释更危险**。

### 4.2 禁止提问用户已经说过的信息

**问题**：`prompts.rs` 第 8 条写的是「最多提出 3 个**真正影响结果**的问题」。「真正影响结果」是主观判断，导致模型把「用户已经说过的信息」也算成缺失。

**修改**：系统提示词 `promptcraft-v2.2.0` → **`promptcraft-v2.5.0`**，在第 8 条之后追加问题自检段。**只追加，不改写既有条款。**

```
问题自检（每个问题输出前逐条过，任一条不通过就删掉该问题）：
1. 这个问题的答案，是否已经出现在用户原文、上下文或附件里？
   是 → 删除。用户已经给过的信息不是缺失信息。
2. 这个问题的答案，是否可以通过合理默认推断出来（且推断错了也不影响产出）？
   是 → 删除。
3. 删完后问题数为 0，且缺失信息并不影响产出内容时，
   改判 enhancement_level 为 none/light，不要为了凑问题而提问。

典型反例（以下问题一律禁止出现）：
- 用户说"帮我翻译一下" → 禁止问"要翻译的原文是什么"
- 用户说"这段录音/这份文档/这段代码" → 禁止问"内容在哪里/请上传/请粘贴"
- 用户说"帮我改一下"并已贴出内容 → 禁止问"你想改哪里"
- 用户说"写个方案"并已给主题 → 禁止问"方案的题目是什么"
```

**版本号说明**：`v2.3.0` 与 `v2.4.0` 是两次已废弃的判据实验，历史记录与实验文档均已引用，**不复用**，故直接落到 `v2.5.0`。

### 4.3 给样本集补「澄清质量」标注

**修改**：`evaluation/samples_v30.yaml` 的 20 条 severe 样本新增 `must_not_question` 字段；`evaluation/verify_enhance.py` 新增第六个机械判定维度。

```yaml
# evaluation/samples_v30.yaml，severe 样本新增
  must_not_question:      # 这些问题的答案用户已经给了，问了就是多余
    - 原文是什么
    - 要翻译的内容
```

**填写规则**：只写「答案确实已出现在用户原话里」的提问内容；每条 1–3 条；能确定就填，不确定就留空。**宁可漏填，不要凑数** —— 误标会产生假阳性，让门禁失真（比没有门禁更坏）。

翻译 3 条必须填（唯一被实测证实的失败案例）：

| 样本 | 原话 | must_not_question |
|---|---|---|
| `v30_translate_generic` | 帮我翻译一下。 | 原文是什么 / 要翻译的内容 |
| `v30_translate_audio_transcript` | 把这段会议录音翻译成英文，我后面要用。 | 录音内容在哪里 / 请上传音频 / 请粘贴转写文本 |
| `v30_translate_two_versions` | （两版本对照翻译） | 两个版本的原文分别是什么 / 请提供原文 |

**新判定函数**（与既有五维并列）：

```python
def judge_dimension_redundant_question(record):
    """维度 6：禁止提问已知信息。问题的答案已出现在原文/上下文里即为冗余提问。"""
    # 归一化后子串匹配（复用既有 normalize_for_match）
    # 命中任一 must_not_question → 严重问题
    # must_not_question 缺失/空 → 「无标注-不判定」，不得记为通过
```

**为什么空标注要单列**：若把「未标注」记为通过，未标注样本会混进分母，让门禁造出虚假绿灯。

## 5. 关键技术决策

### 5.1 为什么不再改 none/light 判据

| 实验 | 做法 | clear 翻转 | medium 翻转 | light 出现（clear/medium） | 结论 |
|---|---|---|---|---|---|
| v2.3.0 | none 判定清单 4 条 | 0% | 10% | **0% / 0%** | ❌ 假绿，功能死 |
| v2.4.0 | light 正向 + 正反例 | 45% | **50%** | 22% / 47% | ❌ 比基线更差 |
| temp 0.1 | 仅温度 | 30% | — | 57% / — | ⚠️ 部分有效 |
| temp 0.0 | 仅温度 | 40% | 26% | 53% / 85% | 🔑 噪声极限仍大量翻转 |

**温度降到 0 仍有 26–40% 翻转，说明漂移不是采样噪声。** 叠加两次判据改写均失败，判定：none/light 边界不是客观可判的划分。

**根本原因**：「这条信息缺了，目标模型是*给不出东西*，还是*给得出但不够好*？」后者不是客观事实。clarify 之所以稳，是因为它的触发条件是客观的（缺少指称对象）。

### 5.2 作废的 1.5× 膨胀阈值

初版规格 §5.2 的「补全后不超过原文 1.5 倍」硬约束**已作废**。

推导链断在中间：v0.3.2 的人工结论（clear 档变差 41.1%、膨胀 ×4.63）发生在 `deepseek-chat` + v2.0 提示词 + **clear 档**上；而 v0.3.5 数据里 **medium 档大量判 light、膨胀同样在 2.6×，恰当率并不比 clear 差**。若膨胀本身有害，medium 应更差。

**「膨胀 = 有害」从未验证。** 至今未对 clear 档的 light 样本做过人工评价 —— 这仍是最大空白。

### 5.3 验收必须双指标联立

v2.3.0 的教训写进本规格：翻转率单独看无效（0% 可能是 light 全判没了）；恰当率单独看无效（奖励「什么都不做」）。两者必须同时满足。

## 7. 验收门槛

**门槛 1 与门槛 3 必须同时满足**（§5.3）。任一不达标不得发布 v0.4.0。

| # | 门槛 | 现状 | 目标 | 验证方式 |
|---|---|---|---|---|
| 1 | clear 档 none/light 翻转率 | 55% | **≤ 30%** | `verify_stability.py --levels clear --repeats 3` |
| 2 | medium 档 none/light 翻转率 | 33% | ≤ 30% | `--levels medium --repeats 3` |
| 3 | **light 出现率不低于基线的 80%** | clear 52% / medium 78% | **clear ≥ 42% / medium ≥ 62%** | 同上（**红线**） |
| 4 | 翻译场景人工盲评命中率 | **11%** | **≥ 60%** | 同盲评表、同 seed、同 20 条 |
| 5 | severe 档整体人工盲评命中率 | 73.3% | ≥ 85% | 同上 |
| 6 | 严重档「问已知信息」条数 | 2/20 条 0 命中 | **0 条** | `must_not_question` 机械判定 |
| 7 | 交付状态漂移 | 0 | 保持 0 | `verify_stability.py` |
| 8 | 既有测试套件 | — | 不回退 | `npm.cmd test`、`pytest evaluation -q`、`cargo fmt/test/clippy` |

**已删除的门槛**（理由见 §5.3 与效果验证报告 §五）：~~180 次恰当率 ≥98%~~（奖励「判 none」）、~~light 膨胀 ≤1.5×~~（依赖未验证假设）、~~clear 翻转 <10%~~（三次实验证明不可达）。

**成本**：稳定性 120 次运行约 $0.26 / 35 分钟；`verify_enhance` 60 条约 $0.12 / 10 分钟；人工盲评 1 轮。

- **收紧 none/light 判据**（已两次失败）

## 10. 诚实边界

1. **30% 仍是高翻转率。** 门槛 1 定在 ≤30% 是「相对现状的改善」，不是「问题已解决」。用户对同一条清晰提示词点两次增强仍可能拿到不同结果。
2. **实验功效不足。** 20 条样本 × 3 次，标准误约 10%；同配置两次独立运行给出 30% vs 71%，噪声地板约 41 个百分点。
3. **人工盲评只有 1 名评审者、20 条、单轮**，无评审者间一致性数据。
4. **「不回答就没法完成任务」这把尺子是新造的**，无对照实验证明它与真实用户感受一致。门槛 4/5 的绝对值只能作**同尺子下的纵向对比**。
5. **「膨胀是否有害」仍未验证**（§5.2），这是本规格最大的已知空白。
6. **不承诺 v0.3.2 发布门槛会通过。**
