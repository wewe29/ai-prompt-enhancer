# PromptCraft v0.3.1-v0.5.0 迭代实施规格

> 文档状态：可直接实施  
> 基于版本：PromptCraft 0.3.0  
> 适用项目：`F:\ai-prompt-enhancer`  
> 编写日期：2026-09-02

## 1. 总体结论

当前项目已经完成 MVP，版本为 `0.3.0`，已有：

- DeepSeek 和 V4-Flash 模型配置。
- 流式生成、停止、重新生成和三轮澄清。
- 原文与增强结果对照。
- 修改接受、拒绝、撤销、重做和手动编辑。
- `none / light / clarify` 增强等级。
- `complete / partial / fallback` 失败降级。
- 本地附件提取、敏感信息检测、历史记录、数据导入导出。
- 评测样本、双裁判和发布门槛。

下一阶段不应继续盲目增加功能，必须依次完成：

1. 发布稳定性。
2. 真实效果验证。
3. 增强结果体验。
4. 安全和数据可靠性。
5. 本地个性化。
6. 更多模型适配。

所有阶段必须按顺序完成，前一阶段未通过验收时不得进入下一阶段。

## 3. v0.3.1：发布稳定性

### 3.1 测试环境

修改：

- `scripts/build-env.ps1`
- `scripts/build-check.ps1`
- `.github/workflows/ci.yml`

要求：

- Vite、pytest、Cargo 的临时目录统一使用 `%TEMP%\PromptCraft-*`。
- 测试结束后在 `finally` 中清理临时目录。
- OpenSSL 未安装时显示明确的安装路径和解决方法。
- 测试失败时区分“代码错误”和“环境错误”。
- CI 必须执行前端、Python、Rust 三类测试。

必须通过：

```powershell
npm.cmd test
npm.cmd run build
python -m pytest evaluation -q
cargo fmt --manifest-path src-tauri/Cargo.toml --all -- --check
cargo test --manifest-path src-tauri/Cargo.toml
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets
```

### 3.2 便携版

修改：

- `scripts/build-portable.ps1`
- `scripts/smoke-test-webview.ps1`

验证流程：

1. 构建便携版。
2. 在全新目录解压。
3. 启动 `PromptCraft.exe`。
4. 配置 DeepSeek API Key。
5. 测试流式生成。
6. 测试停止和重新生成。
7. 测试复制结果和打开目标网页。
8. 测试历史记录保存和恢复。
9. 测试 API 失败时原文仍然保留。
10. 测试附件处理完成后临时文件被清理。

发布要求：

- ZIP 只上传到 GitHub Release，不提交到源码。
- 不提交 `node_modules`、`.venv`、数据库、API Key、浏览器登录状态和评测缓存。
- 更新 SHA-256。
- 未签名版本继续提示 Windows SmartScreen 风险。
- 同步更新 `package.json`、`src-tauri/Cargo.toml`、`tauri.conf.json`、README 和 CHANGELOG 版本号。

## 4. v0.3.2：可信效果验证

### 4.1 评测设置

使用现有：

- `evaluation/samples_v30.yaml`
- `evaluation/run_eval.py`
- `evaluation/release_gate.py`

固定规则：

- 每条样本运行原始组、长度控制组、增强组。
- 每种组合至少重复 3 次。
- 覆盖清晰、中等模糊、严重模糊三种难度。
- 保留 `complete / partial / fallback / hard_failure` 统计。
- 启用第二裁判。
- 至少 20% 样本进行人工盲评。

### 4.2 发布门槛

只有同时满足以下条件，README 才能写具体提升数字：

- 有效交付率不低于 95%。
- 严重模糊任务质量提升不低于 0.8/10。
- 中等模糊任务质量提升不低于 0.4/10。
- 清晰任务变差率不高于 5%。
- 双裁判一致率不低于 75%。
- 人工盲评与自动评测结论方向一致。

未达到门槛时，只能写定性结论：

> 严重模糊任务通常受益，清晰任务应优先保留原文，增强器不保证所有任务都提升。

评测报告必须包含：

- 总体结果。
- 按难度的结果。
- 按任务类型的结果。
- 按目标模型的结果。
- 失败样本清单。
- `partial`、`fallback` 和超时比例。
- 人工盲评结果。
- 是否满足发布门槛。

## 5. v0.3.3：增强结果体验

主要修改：

- `src/views/EnhanceView.tsx`
- `src/App.tsx`
- `src/lib.ts`

保持现有 `EnhancementResult` 字段兼容，不删除旧字段。

结果区域必须显示：

- 增强等级。
- 交付状态。
- 原文和结果字数变化。
- 修改摘要。
- 用户原始事实。
- 模型假设。
- 风险提示及影响范围。
- 当前候选提示词编号。

必须提供：

- 逐项接受修改。
- 逐项拒绝修改。
- 一键接受全部。
- 一键拒绝全部。
- 恢复原文。
- 仅保留必要修改。
- 手动编辑。
- 撤销和重做。
- 重新生成。
- 候选提示词切换。

五个建议必须使用现有 `Suggestion.kind` 标记：

- `goal`
- `context`
- `format`
- `constraint`
- `alternate_intent`

`partial` 和 `fallback` 状态必须：

- 使用非阻塞提示。
- 保留原始输入。
- 保留复制功能。
- 不清空附件。
- 不阻止用户手动编辑。
- 明确告知用户哪些字段缺失。

三轮澄清必须：

- 显示当前轮次。
- 显示剩余轮次。
- 用户拒绝回答时允许继续。
- 信息不足时提供基于明确假设的临时结果。
- 不得在本地虚构数字、事件或事实。

## 6. v0.3.4：安全和数据可靠性

主要修改：

- `src-tauri/src/security.rs`
- `src-tauri/src/attachments.rs`
- `src-tauri/src/storage.rs`

必须补充测试：

- API Key 不出现在普通日志、错误提示或导出包。
- API Key 只保存到 Windows 凭据管理器。
- 敏感信息检测不会静默修改用户原文。
- 附件只作为参考资料，不作为系统指令。
- 附件处理完成后自动删除临时文件。
- 附件删除失败时给出提示。
- 空文件、超大文件、损坏 PDF/DOCX 能安全失败。
- 网络断开、超时、限流、余额不足、模型不存在都有稳定错误码。
- ZIP 导入阻止路径穿越。
- ZIP 导入限制文件数量和总大小。
- 单条历史删除正常。
- 彻底清空会删除历史、设置、费用记录和凭据。
- 导入导出兼容旧版本数据。
- 达到最大占用空间后按配置清理旧记录。

必须继续遵守：

- 不联网搜索。
- 不联网核验事实。
- 数字、真实事件和用户资料以用户提供的内容为准。
- 不记录提示词正文、附件正文或模型回答正文。

## 7. v0.4.0：本地个性化画像

个性化必须采用“本地、可关闭、可解释、可删除”方案。

学习来源只允许包括：

- 用户接受某类修改。
- 用户拒绝某类修改。
- 用户手动编辑后的结果。
- 用户设置的详细程度。
- 用户按任务类型选择的模型或格式偏好。

不得保存：

- 完整聊天记录作为画像。
- 附件原文。
- 公司源码。
- API Key。
- 隐式敏感身份推断。

画像记录至少包含：

- `id`
- `preference_type`
- `value`
- `task_type`
- `evidence_count`
- `confidence`
- `created_at`
- `last_used_at`
- `expires_at`

固定行为：

- 偏好 30 天自动衰减。
- 当前请求始终优先于历史偏好。
- 用户可以查看、编辑、暂停、重置和删除画像。
- 关闭画像后不得向模型发送画像摘要。
- 删除画像后数据库不得保留相关记录。
- 首次启用时必须明确提示用户。
- 不允许静默收集用户内容。

个性化上线前必须验证：

- 用户修改次数是否减少。
- 清晰提示词变差率没有上升。
- 用户可以解释某条偏好为何存在。
- 关闭画像后结果恢复为未个性化行为。

## 8. v0.5.0：模型和供应商扩展

只有前述版本稳定后再实施。

目标：

- 保留 DeepSeek 为默认供应商。
- 保留 V4-Flash 切换。
- 支持 OpenAI 兼容协议的自定义供应商。
- 每个供应商独立保存：
  - API 地址。
  - 模型列表。
  - 默认模型。
  - 输入价格。
  - 输出价格。
  - 连接测试结果。
- 供应商错误不得影响历史数据和原始提示词。
- 不增加自动网页控制、自动粘贴或自动发送功能。

## 9. 实施规则

普通 AI 执行时必须遵循：

1. 先读取项目 README、CHANGELOG、类型定义和相关测试。
2. 一次只实施一个版本阶段。
3. 修改前先确认当前行为和测试覆盖。
4. 不删除用户新增的 `comparison-site`、`website` 或其他未跟踪文件。
5. 不进行无关重构。
6. 每个阶段完成后运行对应测试。
7. 测试失败时先修复测试环境，再判断代码问题。
8. 更新 CHANGELOG 和版本说明。
9. 未通过验收门槛时不得进入下一阶段。
10. 最终报告必须列出修改文件、测试命令、测试结果和未解决风险。

## 10. 首轮执行顺序

第一轮只做以下工作：

1. 建立 `release/v0.3.1` 分支。
2. 修复 Vite、pytest、Cargo 临时目录问题。
3. 修复 OpenSSL 缺失提示。
4. 完成 Windows 10/11 便携版冒烟测试。
5. 运行完整测试集。
6. 更新发布说明和 SHA-256。
7. 发布 `v0.3.1`。
8. 再开始 `v0.3.2` 真实评测。

当前明确不优先开发：

- 自动操作目标模型网页。
- 云端账号和同步。
- 遥测和崩溃数据上传。
- OCR、Excel、PPT 和项目文件夹解析。
- 模型排行榜。
- 复杂的自动画像推断。
- 装饰性界面功能。
