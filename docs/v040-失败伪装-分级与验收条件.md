## 一、分级规则

| 级别 | 判据 | 后果 | 验收人 |
|---|---|---|---|
| **P0** | 会让**发布判定或安全判定直接失真**（可能放行一个坏版本，或造成凭据泄露 / 数据丢失） | 不可发布 | 独立方跑复核器 + 独立方复算 |
| **P1** | 会让**指标或结论失真**，但不直接构成放行 | 结论不可引用 | 作者自测 + 独立方抽查 |
| **P2** | 局部一致性、展示层或文档级问题 | 技术债 | 作者自测 |

**分级不按数量分，按"能不能放行坏版本"分。** 当前 P0 共 17 条、P1 共 23 条、P2 共 1 条；**P0 中已 FIXED 5 条（A1/A2/E2/E3/E5），仍 OPEN 12 条**。

```
② 作者自测（本地全量测试通过）—— 这一步不算验收
      ↓
③ 作者提交 commit，并把 id 清单发回
      ↓
④ 独立方在**干净 checkout 的该 commit** 上跑：
      python scripts\check-fail-open.py
      ↓
⑤ 独立方把「命令 + 实际输出 + commit hash」贴回
      ↓
⑥ 只有 ④ 的输出显示对应 id 已转 FIXED，该条才算闭环
```

**判定纪律**（沿用上一轮教训）：

- 作者自测全绿 ≠ 达标。上一轮"作者自测全绿、实际有 25 处缺陷"。
- **复核器报 `UNVERIFIED` 不等于通过。** 定位不到目标代码块、探针写错，都只报 `UNVERIFIED`，必须由人给结论。
- **同一 commit 必须能复现。** 工作区在途修改会让行号漂移 ⇒ 复核一律基于 commit hash，不是基于工作区。

## 四、复核器

```
scripts\check-fail-open.py
  ├─ 读 docs/v040-失败伪装清单.json
  ├─ 对每条 id 做一次结构探测
  │    ├─ substring_present / substring_absent   （文件级签名）
  │    ├─ guard_in_block / forbidden_in_block    （代码块级守卫）
  │    ├─ regex_forbidden_in_block
  │    └─ manual                                 （只报 UNVERIFIED）
  └─ 输出 OPEN / FIXED / UNVERIFIED；有未闭环 P0 或未判定 P1 ⇒ 退出码 1
```

**为什么用"代码块级守卫"而不是"文件里还有没有这个字符串"**：文件级签名在修复后可能因为别处仍存在同名模式而误报未修（例如 `list_history` 在 UI 列表接口里本来就该存在）。块级探针把"这一段代码里有没有这个守卫"变成可机器判定的问题。**探针误报是噪音，探针漏报是事故** —— 所以块级探针找不到目标块时报 `UNVERIFIED` 而不是 `FIXED`。

## 六、"发布判定"由哪一条命令产出、退出码语义是什么

> WP3-3 明确要求。**这里有三条不同的命令，职责不同，不能混用。**

| 用途 | 命令 | 退出码 | 产物 |
|---|---|---|---|
| **① 发布门禁（唯一放行判据）** | `python evaluation\release_gate.py --summary <summary.json>` | **0 = PASS（可放行）；1 = FAIL（不可放行）** | 逐条门槛的 PASS/FAIL + 作废门槛清单 |
| **② 门禁行为回归** | `python evaluation\check_gate_behavior.py` | **0 = 行为未漂移；非 0 = 门禁行为已漂移** | 5 个 fixture 的判定结果与期望的对照 |
| **③ 失败伪装清单复核** | `python scripts\check-fail-open.py` | **0 = 全部 P0 已闭环且无未判定 P1；1 = 仍有未闭环 P0 或 P0/P1 为 UNVERIFIED** | 41 条逐条 OPEN/FIXED/UNVERIFIED |

### 6.1 放行条件（三条必须同时成立）

```
① release_gate.py           退出码 0
② check_gate_behavior.py    退出码 0
③ check-fail-open.py        退出码 0
```

**任一条非 0 ⇒ 不可发布。** 三条命令都是 **0 次 API 调用**、纯离线可跑。

### 6.2 命令的细节

```powershell
# ① 发布门禁
python evaluation\release_gate.py --summary docs\evaluation-data-v040\fixtures\summary_pass.json
#    判定细则见 docs/v040-验收门禁规范.md（缺口径、样本量、轮次、缺数据行为）

python evaluation\check_gate_behavior.py

python scripts\check-fail-open.py --only A4,A6    # 只复核指定 id 或子族
python scripts\check-fail-open.py --json          # 机器可读
```

**`--only` 同时接受单个 id 与子族字母**（实测：`--only A1` 只跑 A1 一条，`--only A,C` 跑两个子族）。

### 6.3 门禁自身的已知缺口（必须由人补，工具补不了）

1. **A6 的探针是字符串级的**：它探 `if not judge:` 这个模式，而 A6 的行为级闭环（排除计数 + 分母门槛 + 行为回归测试）是它看不见的。⇒ **A6 即使行为上已闭环，复核器仍会报 OPEN** ⇒ 这条只能由人给结论，或把 A6 的 `probe` 改成行为级（**需改 `docs/v040-失败伪装清单.json`，该文件不在本轮我的所有权范围内，故未动**）。

## 七、不依赖作者自测的独立复核路径

> 上一轮的教训：**作者自测全绿 ≠ 达标**（我抓到的 41 条里，作者自测当时全是绿的）。
> 因此验收物必须由**独立一方**在**干净 checkout 的该 commit** 上产出。

### 7.1 为什么"作者自测"不能算数

| 作者自测能证明 | 作者自测**不能**证明 |
|---|---|
| "我改的那处代码现在长这样" | "整条判定链路现在 fail-closed" |
| "我写的那个测试通过了" | "有**别的**测试能抓住这个缺陷的回归" |
| "我的改动没有引入语法错误" | "改动没有把别处的语义改坏" |

**复核器的探针多数是"某个字符串是否还在"**：它能抓住**原地不改**的缺陷，抓不住"换了个写法、bug 还在"的缺陷。⇒ ③ 是**必要不充分**条件，行为级回归测试才是充分条件。

### 7.2 独立复核路径（三条命令，可原样贴进群）

```powershell
# ── 步骤 0：在**干净 checkout** 上做，不碰作者的工作区 ──────────────────
cd D:\workspace\1-projects\ai-prompt-enhancer
$COMMIT = <作者给的 commit hash>
git worktree add D:\Temp\pc-review-$COMMIT $COMMIT
cd D:\Temp\pc-review-$COMMIT

# ── 步骤 1：确认 checkout 的确实是那个 commit ──────────────────────────
git rev-parse HEAD
git status --short          # 必须为空

# ── 步骤 2：跑机器复核（决定性证据） ──────────────────────────────────
python scripts\check-fail-open.py
$REVIEW_EXIT = $LASTEXITCODE

# ── 步骤 3：跑门禁行为回归 ────────────────────────────────────────────
python evaluation\check_gate_behavior.py
$BEHAVIOR_EXIT = $LASTEXITCODE

# ── 步骤 4：跑发布门禁（用 committed fixture，不许用作者本地产物） ──────
python evaluation\release_gate.py --summary docs\evaluation-data-v040\fixtures\summary_pass.json
$GATE_EXIT = $LASTEXITCODE

# ── 步骤 5：贴回「命令 + 实际输出 + commit hash」 ──────────────────────
"commit=$COMMIT  fail_open=$REVIEW_EXIT  gate_behavior=$BEHAVIOR_EXIT  gate=$GATE_EXIT"
```

### 7.3 判定纪律

1. **只有当 ③ 的输出里对应 id 变成 `FIXED`，该条才算闭环。** 作者说"我修了"不算。
2. **`UNVERIFIED` ≠ `FIXED`。** 定位不到目标代码块、探针写错，都只报 `UNVERIFIED`，必须由人给结论。
3. **同一 commit 必须能复现。** 工作区在途修改会让行号漂移 ⇒ 复核一律基于 commit hash，不是基于工作区。
4. **🧪 标记的 4 条（B5/G9/G11/G12）额外要求**：作者必须同时贴出**那条行为级回归测试的失败→修复→再通过三步输出**，只有清单探针的 `FIXED` 不算数。
5. **复核者不是作者。** 作者跑同一条命令，只能证明"脚本能跑通"，不能证明"缺陷已消除"——**同一条命令由不同的人跑，结果才有独立性**。若人手不足，至少由作者在**另一台机器/另一个干净 checkout** 上跑，并把 `git rev-parse HEAD` 的输出一起贴回。
6. **复核产物必须可重放。** 贴回时必须包含：命令原文、完整输出（不是"全部通过"四个字）、`git rev-parse HEAD` 的结果。

### 7.4 一次复核的最小可接受回执

```
commit: <hash>
git rev-parse HEAD → <hash>        # 与上一行一致
git status --short → (空)
命令: python scripts\check-fail-open.py
输出: <完整粘贴，含 OPEN/FIXED/UNVERIFIED 三行统计与逐条明细>
退出码: <n>
命令: python evaluation\check_gate_behavior.py
输出: <完整粘贴>
退出码: <n>
结论: <哪些 id 闭环 / 哪些仍 OPEN / 哪些 UNVERIFIED 需人判>
```

**少任何一项，这次复核就不成立。**
