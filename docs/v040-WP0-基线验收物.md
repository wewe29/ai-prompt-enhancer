本文件是 WP0 的**验收物索引**：四项发布阻断各有一条机器可读的
「修复前失败 / 修复后通过」证据。判定的权威是**探针脚本的退出码**，
不是本文档的表格。

## 一条命令

```powershell
powershell -ExecutionPolicy Bypass -File tools\probe-p0-baseline.ps1
```

- 退出码 **0** = 四项全过；非 0 = 至少一项失败。
- 每项通过时打印一行结论行：`[P0-n] …`。
- 探针实现：`src-tauri/src/probe.rs`（P0-1/P0-2/P0-3 端到端）、
  `src-tauri/src/claims.rs`（P0-4 静态断言）。
- 入口脚本：`tools/probe-p0-baseline.ps1`。脚本自带 `scripts/build-env.ps1` 的
  OpenSSL 环境准备 —— **必须用它**，否则 `libsqlite3-sys` 会回落到空的 `lib\` 目录
  → LNK1181。

## 探针为什么能测出"修复前失败"

探针与产品代码**分离**，且刻意绕开最容易作弊的三种写法：

1. **走真实命令层**（Tauri IPC 的参数反序列化 + 真实命令处理函数），不是直接调内部函数。
   P0-1 的根因正是"命令入参的 serde 行为"——绕过命令层就**测不出它**
   （它在内部函数里看起来完全正常）。
2. **用本机 mock HTTP 端点抓包**：断言的是真实发出去的那次请求的 Authorization 头，
   不是"函数返回了一个看起来对的值"。
3. **P0-2 的攻击者端点跑在本机 HTTP 上**（能通过 base_url 的 HTTPS 校验），
   所以"导入改写端点"在这里是**真实可发生**的，不是理论上的假想。
4. 探针沙箱：独立临时目录 + 独立凭据服务名（keyring `service=PromptCraftProbe-<uuid>`），
   **不触碰真实 PromptCraft 凭据**。

## 已知限制（未解决项）

1. **v0.3.5 时代被改写过端点的机器**：https 形态的恶意地址与"用户自设代理"无法区分，
   读路径不做静默改写，需要在设置页人工确认一次。（A2 的遗留风险）
2. **P0-2 只覆盖"导入包改写端点"这一条路径**。若将来新增别的导入入口
   （云端模板、剪贴板导入…），必须重跑本探针。
3. **P0-4 是静态断言**：它只保证注释不含那几句越界表述、且校准表述不被删光，
   **不校验效果测量方案本身的数据是否又变了**。
   若 `docs/v040-效果测量方案.md` 更新，需同步复核 `src-tauri/src/provider.rs:22-42`。
4. 探针覆盖的是**应用层行为**，不覆盖真实供应商账号的额度/限流（mock 端点只回 SSE 文本）。
